### 第一根因：dry run 计算风暴

Prompt Manager 的 `render()` 默认先调用 `tryGenerate()`，而 OpenAI Prompt Manager 将它实现为 `Generate('normal', {}, true)`。这条 dry run 会执行完整的上下文准备、世界书扫描和 token budget 计算，只跳过真实模型请求。

本次报告中的 16 次 dry run 有 15 次被后续任务标记为 `superseded`，但“替代”只发生在性能记录层。已经进入 Rust `count_openai_token_prefixes` 的任务会在 `spawn_blocking` 中继续遍历 suffix，并对不断增长的完整前缀重复分词，没有取消令牌。最坏时间段连续产生多个重叠 dry run：单次 token 阶段从正常的数百毫秒膨胀到 8.6、12.5、19.7、24.2、30.3、31.8 和 34.5 秒。

聚合结果进一步排除了“真实流式网络导致主要发热”的解释：

- 16 次 dry run 的 generation trace 累计 277.5 s，世界书 214.3 s，token 统计 198.8 s；
- 4 次真实生成的世界书累计 9.85 s，token 统计累计 5.81 s；
- dry-run 时间窗 CPU 平均 98%，真实流式时间窗 CPU 平均 60.7%；
- dry-run 时间窗主线程 busy ratio 平均 0.67，真实流式时间窗为 0.077。

优化不能简单复用上一次 dry-run prompt，因为动态宏、概率、timed effects、扩展事件和聊天状态可能变化。安全边界是：合并尚未开始的重复预览、让最新请求胜出，并使已过期的 token 任务在可验证的条目边界协作取消；任何真正执行的 dry run 仍必须走原来的完整计算。

### 第二根因：已精准归属的扩展监听器

Schema 9 在监听器注册时记录了稳定身份、模块和扩展 ID，因此旧报告中的压缩函数名已经可以归属：

| `third-party/ST-Prompt-Template` | 132 | 145.36 s | 341 ms | 145.02 s | 3.62 s |
| 未归因变量监听器 | 33 | 48.38 s | 227 ms | 48.15 s | 7.95 s |
| `third-party/JS-Slash-Runner` | 90 | 31.75 s | 533 ms | 31.22 s | 10.45 s |
| 核心 `scripts/world-info.js` | 19 | 8.12 s | 18 ms | 8.11 s | 1.29 s |
| `third-party/ST-BaiBai-Tools` | 79 | 2.08 s | 1.21 s | 862 ms | 84 ms |

累计总时长包含父命令等待子命令的嵌套，不能作为独立 CPU 时间相加。`ST-Prompt-Template` 与 `JS-Slash-Runner` 的大部分成本是 await 等待，主要增加端到端延迟；`ST-BaiBai-Tools` 与 Typing Indicator 的同步部分更接近主线程 CPU 成本。

Slash Command 记录显示 `/run` 和内部 `/if` 单次最高约 43.2 s，`/buttons` 最高 20.1 s。它们属于用户自动化的真实执行，不能通过跳过、改并行或改变事件顺序来“优化”。可实施方向仅限于去除框架重复读取/刷新、合并相同派生工作，并由等价性测试证明输出、变量、事件顺序和最终请求体不变。

### 聊天切换与按钮卡顿

聊天切换的 payload 和 DOM 不是当前主瓶颈：

- 加载 31 条消息：总计 4.50 s，消息渲染 230 ms，监听器 3.77 s；
- 加载 23 条消息：总计 3.94 s，消息渲染 308 ms，监听器 3.23 s；
- 加载 1 条消息的最坏样本：总计 19.84 s，消息渲染 28.3 ms，监听器 13.43 s。

按钮 handler 本身也通常很短。发送按钮最坏首个有效帧为 848.6 ms，随后立刻进入 4.51 s 世界书计算，其中 token 统计 3.10 s。消息编辑完成的最坏首帧为 2.93 s，扩展菜单最高 681.6 ms。用户感知的“按钮卡”主要是点击后同步触发的派生工作和主线程拥塞，不是图标或 click handler 本身。

### 流式、内存和发热

移动端流式合帧有效：4 次真实生成共 18,974 chunks，实际 DOM render 3,877 次，约每 4.9 个 chunk 更新一次。格式化累计 2.98 s、DOM commit 675 ms、token 事件监听累计 1.82 s。它仍会造成持续功耗，但不再是数秒冻结的第一原因。

健康采样覆盖 16.1 分钟：进程 CPU 平均 63.1%、P95 88%、最高 291.6%；事件循环延迟 P95 425 ms，最长阻塞 19.1 s。设备没有提供电池温度和电流，因此只能用进程 CPU、主线程 busy ratio、长任务和 RSS 作为发热代理，不能声称已经测得温升或电流改善。

### 当前优化顺序和兼容边界

1. Prompt Manager dry run 使用 latest-wins 调度，避免尚未开始的过期预览进入完整生成流程；
2. 为原生累计前缀 token 统计增加协作取消，过期任务在条目边界退出；
3. 对完全相同且不可变的 token 请求做 single-flight/有界 memo，结果必须逐项等同；
4. 针对已归属扩展，只优化宿主重复工作，不改变扩展代码、事件顺序和 await 语义；
5. 合并同 revision settings 读取和重复保存，保持 API、存储结构与错误语义；
6. 仅对能证明未被扩展同步查询的隐藏 UI 延迟初始化；更激进 DOM 卸载只记录，不直接实施。

所有阶段继续遵守以下硬约束：最终请求体的字段、数组顺序和 provider metadata 不变；世界书激活、预算、宏和 timed effects 不变；事件顺序和 await 语义不变；最终消息仍执行完整 regex、Markdown、sanitize、扩展事件和保存流程。

### 第一严重：串行事件监听器

**位置：**

- `src/lib/eventemitter.js` 的 `EventEmitter.prototype.emit()`；
- 注册到 `user_message_rendered`、`character_message_rendered`、`chat_completion_settings_ready`、`chat_id_changed` 的第一方和第三方扩展处理器；
- Quick Reply、正则、翻译、TTS、记忆等会挂接消息事件的扩展链。

**为什么严重：**

事件总线不是并行调度，而是按顺序执行：

```js
for (i = 0; i < length; i++) {
    await listener.apply(this, args);
}
```

只要其中一个监听器执行自动命令、读取设置、扫描内容、保存数据或等待其他异步任务，整个事件就无法结束。后面的监听器、请求 dispatch、下一帧和用户输入都会一起等待。

最新报告中的三个主要慢监听器为 Release 压缩名：

| 监听器 | 触发点 | 累计耗时 | 单次耗时 | 导致的表象 |
| --- | --- | ---: | ---: | --- |
| `qf` | 用户/AI 消息渲染完成 | 31.86 s | 2.43–3.68 s | 发送消息后卡住、输出结束后卡住 |
| `jf` | Chat Completion 请求体准备完成 | 10.79 s | 2.60–2.89 s | 世界书完成后仍迟迟不真正发请求 |
| `Gf` | 聊天 ID 切换 | 5.39 s | 2.67–2.72 s | 切换聊天时界面停住 |

这三个监听器占最近 100 条慢监听总耗时的 **93.6%**，是当前最明确的主线程冻结来源。

**目前不能确定的部分：** `qf/jf/Gf` 是压缩后的函数名，现有报告没有记录注册模块和插件 ID。Quick Reply 自动执行的触发事件与它们高度重合，是高风险候选，但现阶段不能严谨断言三个函数全部属于 Quick Reply。必须先补稳定监听器身份，再修改具体处理器；不能直接把所有事件改成并行，否则会改变插件执行顺序和最终请求体。

### 第二严重：世界书精确 token 计数

**位置：**

- `src/scripts/world-info.js` 的世界书收集、递归扫描、预算判断和 prompt build；
- `src/scripts/tokenizers.js` 的精确 token 计数与缓存；
- `/api/tokenizers/openai/count-prefix-batch` 对应的 Tauri/Rust tokenizer 路径。

**为什么严重：**

世界书不是只遍历一次条目。它会进行 3–5 轮递归扫描，筛选激活条目，并根据 token budget 决定可以插入多少内容。预算判断需要知道“当前累计世界书文本”的精确 token 数。

如果每加入一条内容都重新 tokenize 整个累计前缀，计算量会随内容增长不断放大。约 4,500–5,300 条候选、几十到上百条激活内容，再叠加 tokenizer cache miss、动态宏和 dry-run/真实生成重复准备，就会形成秒级甚至历史上的分钟级等待。

旧样本中，世界书单次 token 计数达到 85–217 秒，而条目扫描只有约 0.3–0.4 秒，证明根因不是排序或关键词匹配。批处理和预算短路落地后，最新结果已降为：

- 世界书完整阶段平均 2.77 秒、最大 5.31 秒；
- token 计数平均 1.85 秒、最大 4.22 秒；
- 条目扫描平均 498 毫秒；
- 条目准备、克隆和收集平均约 405 毫秒。

因此世界书已经明显改善，但精确 token 计数仍占世界书成本的约三分之二，是第二严重热点。

### 第三严重：流式输出反复全量格式化

**位置：**

- `src/script.js` 的 `StreamingProcessor`；
- 输出正则、Markdown 渲染、HTML sanitize、reasoning 更新和 DOM commit；
- `src/scripts/tauri/perf/streaming-render-policy.js` 的移动端刷新频率策略。

**为什么严重：**

模型每次只新增少量字符，但中间预览通常重新处理“从开头到当前”的完整文本。输出长度不断增长，后续每次正则、Markdown 和 sanitize 都比前一次更贵。即使每次只花几毫秒，数百或上千次累积后也会持续占用 CPU，使手机无法降频。

最新 6 次真实生成共收到 23,147 个 chunk/token 事件，生成 16,622 个字符，却执行了 5,673 次格式化：

- `format-total` 累计 8.67 秒；
- sanitize 累计 3.17 秒；
- 输出正则累计 3.01 秒；
- Markdown 累计 2.31 秒；
- DOM commit 累计 1.33 秒；
- 最重一次 3,911 字符输出执行 1,058 次格式化，总格式化耗时 4.77 秒。

这一项更偏向“持续发热和掉帧”，不是发送瞬间 3 秒冻结的第一原因。移动端限频已经减少预览次数，但没有消除每次重新处理完整输出的算法成本。

### 第四严重：常驻 DOM 和内存基线过高

**位置：**

- SillyTavern 主页面、设置抽屉和模板；
- 启用扩展创建的面板、菜单、Quick Reply UI、iframe/runtime；
- WebView renderer 及其 JS/DOM 状态。

**为什么严重：**

最新采样中只有 0–7 个消息节点，但整个页面始终有约 2.1 万个 DOM 节点。这说明聊天楼层不是 DOM 基线的主要来源，大量不可见设置页、抽屉和扩展 UI 在未使用时也常驻。

节点多不会自动等于每一帧都慢，但会放大：

- 样式失效和布局计算；
- `querySelector`、jQuery 全局查找和事件委托；
- 抽屉首次显示时的呈现延迟；
- GC、DOM wrapper 和字符串的内存压力；
- 扩展互相观察 DOM 时的 MutationObserver 成本。

这与扩展菜单稳定需要约 0.51–0.55 秒显示相符。RSS 在约 375–532 MiB 间波动，说明移动端性能余量偏小，但当前数据不足以证明存在单调内存泄漏。

### 次级问题：重复设置和扩展版本请求

**位置：**

- `src/scripts/extensions.js` 的第三方扩展版本检查；
- `src/script.js`、Quick Reply、世界书等对 `/api/settings/get` 的调用；
- Tauri embedded routes 到 Rust command 的设置和 Git/version 操作。

**为什么发生：**

不同模块各自需要完整设置，没有共享同一轮 in-flight 读取；扩展更新检查又会按每个扩展单独执行。它们会增加 I/O、序列化、Git 操作和后台 CPU 唤醒。

它们不是当前发送/结束输出冻结的核心原因：模型 generate endpoint 本地 dispatch 只有约 20–69 毫秒，直接 Tauri channel 多数也在几十毫秒。优化这部分主要改善启动、扩展页打开和耗电，不应优先于监听器、世界书和流式处理。

## 3. 执行模型与性能边界

生成与聊天交互的关键路径可以简化为：

```text
用户点击
  -> WebView 事件分发
  -> SillyTavern 前端状态和扩展监听器
  -> 上下文准备
  -> 世界书收集、扫描和 token 预算计算
  -> 最终请求体组装
  -> Tauri embedded route / Rust command
  -> 模型流式响应
  -> 正则、Markdown、sanitize、DOM commit
  -> 消息保存和结束事件监听器
```

其中大部分可见卡顿发生在 WebView 主线程。当前 `EventEmitter.emit()` 会按注册顺序逐个 `await` 监听器：

```js
for (i = 0; i < length; i++) {
    await listener.apply(this, args);
}
```

这保证了原有事件顺序，却也意味着任意一个慢扩展或监听器都会阻塞其后的监听器、生成调度和下一帧。优化时不能简单改成 `Promise.all()` 或 fire-and-forget，否则会改变插件顺序、状态可见性、自动命令执行和最终请求体。

## 4. 总体结论

当前性能问题不是单一热点，而是四类成本叠加：

1. **P0：串行事件监听链**。它是当前发送、生成开始、消息落盘、生成结束和聊天切换时数秒冻结的直接来源；
2. **P0：世界书精确 token 预算**。它曾是超大世界书的绝对瓶颈，现已获得数量级改善，但在 4,500–5,300 条目规模下仍需约 1–5 秒；
3. **P1：流式期间重复全量格式化**。移动端已限频，但正则、Markdown、sanitize 和 token 事件仍持续占用 CPU，是发热的重要来源；
4. **P1：过大的常驻 UI/扩展 DOM 与内存基线**。只有 0–7 个消息节点时，页面仍常驻约 2.1 万 DOM 节点和约 375–532 MiB 原生 RSS，增加了布局、样式计算、GC 和内存带宽压力。

网络和 Tauri IPC 不是生成卡顿的首要根因，但重复设置读取、扩展版本检查和持久化操作会增加启动/切换延迟与后台唤醒。

## 6. 分项分析

### 6.1 事件监听器：当前最高优先级

最新报告中，最近 100 条慢监听器累计耗时 **51.33 秒**。前三个压缩后函数占 **48.03 秒（93.6%）**：

| 监听器（Release 压缩名） | 事件 | 次数 | 累计 | 单次范围 |
| --- | --- | ---: | ---: | ---: |
| `qf` | `user_message_rendered` / `character_message_rendered` | 11 | 31.86 s | 2.43–3.68 s |
| `jf` | `chat_completion_settings_ready` | 4 | 10.79 s | 2.60–2.89 s |
| `Gf` | `chat_id_changed` | 2 | 5.39 s | 2.67–2.72 s |

这三个阶段分别位于：

- 用户消息加入后；
- AI 消息保存/渲染后；
- Chat Completion 请求体准备完成、真正发起生成前；
- 聊天 ID 切换后。

它们与“发送卡”“结束卡”“切换聊天卡”完全同相。5 次聊天加载总计 31.08 秒，其中 `chat-changed-listeners` 为 19.41 秒，而 `messages-render` 仅 163.9 毫秒。即使把消息渲染继续优化一倍，对总加载时间也几乎没有影响。

当前只能确认事件和耗时，不能仅凭 `qf/jf/Gf` 精确归属扩展：Release 构建会压缩函数名，报告尚未记录注册模块、源码位置或插件 ID。Quick Reply 是高风险候选，因为它在用户消息、AI 消息、聊天切换、世界书激活和生成前串行执行自动命令；现场交互中也存在大量 Quick Reply 菜单脚本。但在获得稳定监听器身份前，不能把候选当成最终根因。

性能插件自身的 `CHARACTER_MESSAGE_RENDERED` 处理只写入一个时间戳，不可能解释 2–4 秒延迟。监听器测量只在采集期间增加 `performance.now()` 和一条轻量记录，有非零开销，但也不足以制造秒级冻结。

**结论：** 下一步最有价值的工作不是继续猜测扩展，而是给监听器记录稳定身份，然后优化已确认的慢函数内部工作。

### 6.2 世界书：已从灾难级降到秒级，仍需继续收敛

#### 历史最坏情况

Schema 3 的超大世界书包含约 4,524–4,589 个全局条目和 839 个角色条目，排序后约 5,363–5,428 条。三次完整样本中：

- 世界书总耗时：86.11 s、105.20 s、217.85 s；
- `token-count`：85.31 s、104.27 s、217.02 s；
- `entry-scan`：326–411 ms；
- 条目收集、准备和克隆约 450–463 ms。

当时 **99% 左右的世界书耗时来自 token 计数**，不是关键词匹配、排序或条目扫描。原实现会为不断增长的累计前缀反复请求精确 token 数，既重复传输长字符串，也重复 tokenize 已计算过的前缀。

#### 当前结果

批量计数、累积前缀批处理和预算短路落地后，Schema 4 的 13 次完整世界书扫描为：

| 阶段 | 平均 | P50 | 最大 | 累计 |
| --- | ---: | ---: | ---: | ---: |
| 世界书完整扫描 | 2.77 s | 2.82 s | 5.31 s | 36.07 s |
| `token-count` | 1.85 s | 1.75 s | 4.22 s | 24.02 s |
| `entry-scan` | 498 ms | 543 ms | 644 ms | 6.48 s |
| `entries-total` | 405 ms | 437 ms | 518 ms | 5.27 s |

现场数据表明世界书已获得数量级改善。因为两次报告不是严格相同的世界书、缓存和生成状态，不能宣称固定的百分比，但可以确认旧的 85–217 秒精确计数路径已不再出现。

当前世界书成本构成约为：

- token 计数：66.6%；
- 条目扫描：18.0%；
- 条目收集/准备/克隆：14.6%；
- 排序、分组、事件和 prompt build：不足 1%。

所以继续微调排序没有实际收益。后续应集中在：

1. 按“内容 + tokenizer/model + 影响 tokenization 的配置”复用精确计数；
2. 避免相邻 dry-run/真实生成重复准备同一份不可变世界书快照；
3. 保持预算命中后的短路，仍正确处理 `ignoreBudget`、概率、宏替换和动态内容；
4. 将可并行、无副作用的 tokenize 移到 Rust/worker，但不得改变激活顺序和最终插入内容。

### 6.3 流式生成：限频有效，但仍有重复全量工作

Schema 4 的 6 次真实流式生成共处理：

- 23,147 次 token/chunk 事件；
- 最终输出 16,622 字符；
- 5,673 次预览格式化；
- `format-total` 累计 8.67 秒，平均每次生成 1.44 秒，最重一次 4.77 秒；
- token 事件监听器累计 2.60 秒；
- DOM commit 累计 1.33 秒。

格式化内部主要成本：

| 阶段 | 6 次累计 |
| --- | ---: |
| HTML sanitize | 3.17 s |
| 输出正则 | 3.01 s |
| Markdown | 2.31 s |

移动端流式预览已按设备和可见性限制刷新频率，因此预览次数低于 chunk 数；但每次刷新仍会处理不断增长的完整输出，长文本与复杂正则会放大成本。最后一次 3,911 字符输出进行了 1,058 次格式化，单次生成的格式化总成本达到 4.77 秒，其中正则 2.26 秒、sanitize 1.56 秒、Markdown 0.90 秒。

真实生成期间最大长任务仍达到 2.65–3.72 秒。不过这些长任务有一部分与生成开始/结束的慢监听器重合，不能全部归因于流式格式化。流式的明确问题是持续、频繁、小块 CPU 工作，它更容易造成设备长期升频和发热，而不是只造成一次明显冻结。

后续方向应是：

- 中间预览只保留最新任务，旧的待渲染任务可合并；
- 把高亮、复杂扩展后处理等非关键工作推迟到空闲期或最终帧；
- 评估可证明等价的增量解析，无法证明等价时保留最终一次完整格式化；
- 最终消息必须执行完整正则、Markdown、sanitize 和 DOM commit，且最终 HTML 与当前实现一致；
- 不减少对外可观察的最终 token、消息事件和保存行为。

### 6.4 聊天加载、长聊天与滚动

最新 5 次聊天加载仅包含 1–5 条可见消息：

| 阶段 | 平均 | 最大 |
| --- | ---: | ---: |
| 完整聊天加载 | 6.22 s | 7.97 s |
| `chat-changed-listeners` | 3.88 s | 4.79 s |
| payload read | 27.4 ms | 56.2 ms |
| `messages-render` | 32.8 ms | 62.2 ms |

对应 5 次 `messages-redisplay` 操作平均 28.7 毫秒、最大 54.6 毫秒。这说明 windowed payload 和少量消息 DOM 渲染已经不是当前聊天打开的首要成本。

历史上快速向上翻楼层会一次性创建多个复杂消息节点，主线程在一帧内无法完成，用户看到“楼层加载不出”。当前实现已经：

- 按小批次 prepend 历史楼层，并在批次之间让出一帧；
- 保持插入前后的滚动锚点；
- 统一生成、发送、消息落盘和分页的滚动所有权；
- 在用户主动离开底部时不强制跟随流式输出。

但最新报告没有采到大量历史楼层连续分页，不能据此宣布该路径完全解决。专项复测需要覆盖 200、500、1,000 楼聊天，连续快速触发 `showMoreMessages`，记录每批 DOM 创建、锚点修正、图片/iframe hydration 和 `MORE_MESSAGES_LOADED` 监听器。

### 6.6 DOM、内存与潜在 GC 压力

最新 935 秒健康采样中：

- DOM 节点：20,688–21,944；
- 可见消息节点：0–7；
- 原生进程 RSS：392.8–558.2 MB（约 375–532 MiB）；
- WebView JS used heap：固定报告约 462 MB；
- JS total heap：固定报告约 521 MB。

只有极少消息时仍有约 2.1 万 DOM 节点，说明常驻成本主要来自应用框架、抽屉、设置页、扩展 UI、隐藏模板和消息外部组件，而不是当前可见楼层。隐藏节点仍可能参与样式失效、查询、事件委托和内存保留。

RSS 在采样期波动约 158 MiB，但目前没有证据证明单调泄漏。JS heap 数值长期不变更像 WebView 的粗粒度/受限暴露，不能作为“内存稳定”的证据。需要用重复场景和回落观察判断泄漏：连续切换角色、打开/关闭抽屉、生成、删除消息后，强制进入稳定空闲窗口，再观察 RSS 与 DOM 是否回到基线区间。

已有的 token cache 分桶、Prompt Inspector record 懒加载、windowed payload、角色浅索引和资源缓存降低了冷启动与大数据常驻，但没有消除扩展 DOM 和 WebView renderer 本身的基线。

### 6.7 网络、embedded route 与 IPC

最新报告记录 135 个请求，121 成功、14 失败/取消，并发峰值为 5。主要重复路径：

| 路径 | 次数 | P50 | 最大 | 累计 |
| --- | ---: | ---: | ---: | ---: |
| `/api/extensions/version` | 19 | 1.15 s | 1.27 s | 17.45 s |
| `/api/settings/get` | 12 | 623 ms | 1.21 s | 8.83 s |
| `/api/settings/patch` | 12 | 299 ms | 935 ms | 4.45 s |
| `/api/characters/get` | 4 | 190 ms | 1.16 s | 1.60 s |
| `/api/backends/chat-completions/generate` | 7 | 51 ms | 69 ms | 326 ms |

`/api/extensions/version` 有 10 次成功、4 次 500 和 5 次 AbortError。它通常来自多个第三方扩展的 Git/version 检查；虽然已有并发队列，但同一波检查仍会产生大量 Rust/文件/Git 工作。该路径不是发送生成卡顿的直接主因，却会增加启动/打开扩展页时的 I/O、CPU 和耗电。

`/api/settings/get` 通过 embedded route 调用 Rust 聚合设置。当前已有后端缓存和 patch save，但前端的启动、Quick Reply、世界书等入口仍可能重复取完整设置。应在不改变可见新鲜度的前提下共享同一 in-flight promise 或版本化快照。

报告中的直接 Tauri `invokeInFlight` 始终为 0，因为多数调用隐藏在同源 embedded HTTP route 后面。这是埋点边界，不代表没有 Rust command 或 IPC。

### 6.8 发热与能耗

健康采样能确认：

- 约 935 秒内累计记录 73.99 秒长任务；
- 主线程 busy ratio 平均 7.6%，P95 41%，P99 99%；
- event loop lag P99 2.78 秒，最大 5.77 秒；
- 单采样窗口 long task 最大 6.04 秒；
- 进程 CPU ticks 从 75,201 增至 127,534；
- 设备报告 8 个逻辑 CPU。

但以下原生字段全部缺失：

- `processCpuPercent`；
- `systemCpuTicks`；
- 电池温度；
- 电流、电压和充电状态。

Android 上 `/proc/stat` 和 `/sys/class/power_supply/...` 可能受权限或设备路径限制。现阶段只能从持续格式化、tokenization、长任务和 CPU ticks 增长推断 CPU 压力，不能声称具体温升由某函数造成。

发热最可能由两类负载共同构成：

1. 生成前数秒高强度世界书/token/插件工作，使 CPU 短时满载；
2. 数分钟流式输出中的高频正则、sanitize、Markdown、事件和 DOM 提交，使 CPU 长时间无法降频。

后续应通过 Android 原生平台能力采集进程 CPU 时间、电池温度/电流（设备允许时），并计算相邻样本增量；不应继续只读取可能被系统屏蔽的 sysfs 文件。

## 7. 已落地优化与当前效果

| 方向 | 当前实现 | 证据/状态 |
| --- | --- | --- |
| 性能可观测性 | Perf 扩展、世界书/流式/generation/chat trace、监听器和运行时诊断 | Schema 已演进至 4；仍缺稳定监听器身份和完整原生能耗 |
| 世界书排序 | 避免重复排序索引查找 | 当前排序单次约 0.8–1.3 ms，已不是瓶颈 |
| 世界书 token | OpenAI 批量精确计数、累计前缀批处理、预算命中短路 | 最坏现场值从 217 s 降到 4.22 s；需同负载复测 |
| 流式预览 | 移动端和后台状态限制预览刷新率 | 格式化次数低于 chunk 数，但长输出仍可累计 4.77 s |
| 长聊天楼层 | 分批 prepend，每批间让出一帧 | 小样本操作最大 54.6 ms；缺少大聊天快速翻页复测 |
| 滚动行为 | 集中滚动控制、保留 viewport、尊重用户 scroll lock | 已修复发送/结束输出抢占滚动的实现根因，需持续回归 |
| 聊天存储 | windowed payload、历史按需 backfill、页缓存和批量 IPC | 可见消息渲染已不是聊天打开瓶颈 |

| 设置与资源 | 设置聚合缓存、增量 patch、Host Resource 条件缓存 | 降低重复磁盘读取；前端仍存在重复 settings/version 请求 |

## 8. 根因分层

### 8.1 已证实

1. 事件总线串行等待慢监听器，直接造成 2–4 秒冻结；
2. 历史世界书瓶颈是累计前缀精确 token 计数，不是排序；
3. 当前世界书 token 计数仍是世界书最大阶段；
4. 流式期间正则、sanitize 和 Markdown 重复执行，形成持续 CPU 负载；
5. 聊天切换主要耗时在监听器，不在 payload 读取或少量消息渲染；
6. 页面在极少消息时仍有约 2.1 万 DOM 节点和高 RSS 基线；
7. 扩展版本检查和完整 settings 读取存在重复调用。

### 8.2 高置信但尚未精确归属

1. `qf/jf/Gf` 很可能来自启用的扩展或自动化脚本，但函数名已压缩；
2. Quick Reply 自动执行链与慢事件覆盖高度一致，是重点候选，但不能在没有稳定 ID 的情况下定罪；
3. 扩展菜单约 500 ms 延迟很可能来自面板展开后的布局/样式/内容初始化，而不是 click handler；
4. 持续流式格式化是发热来源之一，但缺少 CPU 与温度数据，无法量化占比。

### 8.3 尚未证实

1. RSS 波动是否为内存泄漏；
2. 最新长聊天快速翻页是否仍会长时间空白；
3. 3.79 秒未知点击对应哪个控件或插件；
4. 某个具体第三方扩展是否独占 `qf/jf/Gf`；
5. 网络请求是否直接阻塞主线程。当前多数网络耗时与主线程冻结没有一一对应。

## 9. 后续优先级

### P0：先把慢监听器定位到源码和插件

埋点应在监听器注册时分配稳定 ID，记录：

- event 名；
- 注册顺序；
- 模块/扩展 ID；
- 开发态源码位置，Release 至少记录构建期模块 ID；
- 是否由 `on`、`once`、`makeFirst`、`makeLast` 注册；
- 当前 generation/chat-load run ID；
- 自身同步耗时、await 耗时和嵌套 slash/Quick Reply 命令耗时。

定位后，针对具体监听器选择缓存、减少重复读取、拆分 UI 更新、合并保存或在契约允许处让出帧。不得全局并行化 EventEmitter。

### P0：守住世界书现有收益并继续减少重复计数

- 为稳定内容建立有版本边界的 token memo；
- dry-run 与随后的真实生成共享不可变准备结果时，必须验证动态宏、概率、timed effects 和事件副作用；
- 对相同世界书连续生成建立冷/热缓存对照；
- 保留预算短路后的 `ignoreBudget` 和最终 prompt 顺序；
- 用请求体快照测试确保优化前后最终请求完全等价。

### P1：降低流式稳态 CPU

- 合并待处理的中间预览，只渲染最新累计文本；
- 将非关键高亮/装饰推迟到空闲期或最终消息；
- 对正则、Markdown、sanitize 分别增加输入长度、规则集和调用方埋点；
- 最终完整渲染不可省略；
- 以主线程 busy ratio、每千字符格式化次数和最大长任务作为验收指标。

### P1：处理重复设置和扩展版本请求

- 对同一 settings revision 共享 in-flight read；
- 审计 Quick Reply、世界书和启动流程是否各自读取完整 settings；
- 扩展版本检查按 extension ID 去重并缓存短期结果；
- 自动检查与手动打开扩展页重叠时复用正在进行的任务；
- 失败/取消必须保留当前 UI 语义，不得把旧结果伪装成最新结果。

### P1：降低常驻 DOM 基线

- 按模块统计 DOM 节点、事件监听器和 detached nodes；
- 抽屉内容按首次打开初始化，关闭后仅保留必要状态；
- 不可见复杂面板评估 `content-visibility` 或真正卸载，但必须验证插件查询和表单状态；
- 查找重复模板、重复 Quick Reply UI、隐藏 iframe 和消息外 runtime；
- 任何卸载策略都必须保留第三方扩展可观察的 DOM 契约。

### P2：补齐发热与长聊天证据

- 原生采样改用 Android 可用的平台 API，并用相邻样本计算 CPU 百分比；
- 对无法读取温度/电流的设备明确标记 capability，而不是持续输出 `null`；
- 增加 `showMoreMessages`、分页 IPC、每批 render、图片/iframe hydration 和滚动锚点 trace；
- 增加 20 次生成/切换循环后的 RSS、DOM 和 idle 回落分析。

### P3：高风险架构优化

以下方向只有在 P0/P1 完成后才值得考虑：

- 世界书扫描或纯 tokenize 移入 worker/native；
- 可证明等价的增量 Markdown/HTML pipeline；
- 扩展事件声明只读/可并行能力；
- 更激进的消息虚拟化。

这些改动跨越插件兼容、DOM 生命周期和请求构造边界，收益可能高，但回归风险也最高。

## 10. 不可破坏的行为契约

所有优化必须满足：

1. 最终请求体字段、顺序敏感数组、世界书注入内容和 token budget 结果与基线一致；
2. 世界书激活顺序、概率、递归扫描、timed effects、`ignoreBudget` 和宏替换语义不变；
3. EventEmitter 的既有顺序和 await 语义默认不变，只有逐个监听器证明无依赖后才能调整；
4. 最终流式消息必须经过完整正则、Markdown、sanitize、扩展事件和保存流程；
5. 发送、生成结束、切换聊天和历史 prepend 不得抢占用户当前 viewport；
6. windowed chat 的楼层 ID、编辑、删除、swipe 和 prompt backfill 语义不变；
7. 第三方扩展依赖的事件名、DOM 钩子、API 路径和存储结构不因优化静默变化；
8. 缓存只优化性能，失效或冷启动时必须回退到正确的完整计算。

建议为最终请求建立双执行验证：同一冻结输入分别运行基线和优化实现，比较 canonical JSON、消息数组、世界书片段、采样参数和 provider-specific metadata；不应只比较 token 总数或字符串长度。

## 11. 建议验收基线

以下是工程目标，不是浏览器标准阈值：

| 场景 | 建议目标 |
| --- | --- |
| 普通按钮交互 | P95 首个有效帧 < 100 ms，非网络型最大值 < 250 ms |
| 发送到请求 dispatch | 大世界书热缓存 P95 < 2 s；不得出现 > 1 s 的单个未知监听器 |
| 聊天切换 | 监听器总计 P95 < 500 ms；1–20 可见楼层完整加载 P95 < 1.5 s |
| 世界书 | 约 5,000 条时 token 阶段 P95 < 2 s，完整阶段 P95 < 3 s |
| 流式稳态 | 每秒无 > 200 ms 长任务；中间预览可合并，最终结果必须完整一致 |
| 长聊天翻页 | 每批主线程占用 < 50 ms，连续翻页不出现 > 250 ms 输入阻塞 |
| 内存稳定性 | 20 次场景循环后无单调增长；空闲回落后的 RSS 增量 < 50 MiB |
| 发热 | 记录 CPU%、温度/电流能力；同场景优化后 CPU time 与能耗趋势下降 |

目标需要在固定设备基线验证后调整，不能仅凭一次现场数据判定通过。

## 12. 复测矩阵

## 13. 埋点缺口

当前 Schema 4 已能回答“哪个阶段卡”，但还不能完整回答“哪个模块为什么卡”。下一版应补充：

1. 监听器稳定 ID、注册模块和插件 ID；
2. slash command / Quick Reply 单条命令 trace；
3. `showMoreMessages` 与分页/锚点 trace；
4. 格式化规则集、输入长度和调用方；
5. DOM 节点按模块统计与 detached node 计数；
6. embedded route 到 Rust command 的关联 ID；
7. Android CPU%、温度、电流 capability 与增量；
8. target 被移除前的交互路径快照；
9. Top-N 丢弃计数，区分“保存 100 条”和“总共 100 条”；
10. 用 trace `runId` 与 generation/chat-load record 做强关联，迟到的异步 measure 不得写入其他 run；
11. profiler 自身 CPU/内存开销的 A/B 基线。

性能 JSON 会包含控件名称、扩展脚本可访问文本和用户文件路径。原始报告应留在本地，不直接提交仓库；共享前应脱敏，仅保留聚合指标和稳定匿名 ID。

## 14. 最终判断

TauriTavern 的性能问题已经从“缺少证据的整体卡顿”收敛为几个明确热点：

- 世界书历史灾难级 token 计数已经显著改善，但大世界书仍有 1–5 秒准备成本；
- 当前最严重、最直接的冻结来自串行事件监听链，而不是发送按钮、消息 DOM 或模型网络；
- 流式限频降低了刷新次数，但重复格式化仍会造成持续 CPU 压力和发热；
- 高 DOM/RSS 基线使移动 WebView 缺少余量，扩展和复杂面板会进一步放大布局与 GC 成本；
- 网络/IPC 的重复设置读取和扩展版本检查属于次级但可稳定回收的成本；
- 现有埋点足以确定优化优先级，但必须补齐监听器归属和 Android 能耗数据，才能继续做精准优化。

下一阶段应先定位并处理 `qf/jf/Gf` 对应的真实监听器，再继续降低流式稳态 CPU。此顺序对用户可见卡顿的收益最大，也比全局修改事件模型或重写渲染架构风险更低。
